# Quant Research Lab — Milestone 8: Live Market Data & Automated Paper Trading

Milestones 1–7 have been implemented. Continue developing the existing Quant Research Lab repository according to the original blueprint and updated development roadmap.

Do not restart the project, unnecessarily rewrite existing components, or break existing functionality.

## Primary Objective

Build a reliable, autonomous paper-trading infrastructure that can run validated quantitative strategies using live market data, generate trading signals, execute simulated orders, manage virtual portfolios, enforce risk constraints, and record all trading activity.

The system must support both traditional systematic strategies and machine-learning-based trading strategies.

**The objective is to evaluate whether strategies that performed well historically can operate reliably under real-time market conditions.**

Paper trading must remain completely isolated from real-money trading.

No live brokerage orders may be submitted during this milestone.

## 2. Live Market Data Infrastructure

Extend the existing market-data architecture to support live streaming and polling.

### Supported Markets

Initially support:

- US equities.
- ETFs.
- ES futures.
- MES futures.
- NQ futures.
- MNQ futures.

Use provider adapters so that different market-data vendors can be supported.

Potential providers include Alpaca for equities and an appropriately licensed futures data provider.

Do not assume an existing historical-data provider supports real-time streaming.

### Requirements

- Real-time market data ingestion.
- WebSocket support where provided.
- Polling fallback where appropriate.
- Streaming OHLCV bars.
- Trade and quote ingestion where available.
- Reconnection handling.
- Heartbeat monitoring.
- Data timestamp validation.
- Duplicate event detection.
- Out-of-order event handling.
- Missing data detection.
- Market session awareness.
- Timezone normalization.
- Rate-limit handling.
- Historical data gap recovery.

Clearly distinguish real-time, delayed, and replayed market data.

A provider reporting delayed quotes must not be presented as real time.

### Data Normalization

Convert all incoming data into consistent internal market events.

Each event should identify:

- Instrument.
- Provider.
- Event timestamp.
- Receive timestamp.
- Data type.
- Price and volume information.
- Session context.
- Sequence identifier where available.

Reuse the existing historical event model when practical.

## 3. Paper Trading Execution Engine

Implement a broker-independent simulated execution system.

The paper execution engine should receive trading orders generated by the strategy and portfolio systems.

### Order Types

Support initially:

- Market orders.
- Limit orders.
- Stop orders.
- Stop-limit orders where practical.
- Order cancellation.
- Order replacement where appropriate.

### Order Lifecycle

Implement explicit order states:

- CREATED
- PENDING
- ACCEPTED
- PARTIALLY_FILLED
- FILLED
- CANCELLED
- REJECTED
- EXPIRED

Ensure order state transitions are validated.

### Fill Simulation

Simulate execution using observable market conditions.

Account for:

- Bid/ask spreads.
- Commission and exchange fees.
- Slippage.
- Available quote or trade information.
- Order latency.
- Partial fills when supported by the data.
- Market hours.
- Contract tick sizes.
- Instrument-specific lot sizes.

Do not assume all market orders fill at the last traded price.

Do not assume that a displayed quote guarantees a fill.

If only OHLCV bars are available, use a conservative and clearly documented bar-based fill model.

The execution engine must never claim that simulated fills are equivalent to guaranteed real fills.

## 8. Portfolio and Strategy State Persistence

The system must recover reliably after restarts.

Persist:

- Paper account balances.
- Open positions.
- Open orders.
- Order lifecycle state.
- Historical fills.
- Strategy states.
- Active model versions.
- Risk limits.
- Strategy allocations.
- Latest processed market events.
- Trading session information.

Use durable local storage, such as SQLite or PostgreSQL, depending on the existing architecture.

Do not introduce unnecessary infrastructure.

### Restart Recovery

On restart:

1. Load the previous account state.
2. Reconstruct open positions and pending orders.
3. Verify accounting consistency.
4. Detect gaps in market data.
5. Reconcile strategy and portfolio state.
6. Prevent duplicate orders.
7. Resume only when safety checks succeed.

If state reconciliation fails, suspend trading and report the issue.

```yaml

  enabled: true

  provider: configured_provider
  mode: delayed_or_realtime

  mode: simulated

  max_daily_loss_pct: 1.0
  max_portfolio_drawdown_pct: 10.0

```

Treat these values as example configuration defaults, not optimal risk settings.

Live brokerage execution must remain unavailable through this configuration.
